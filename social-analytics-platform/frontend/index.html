Design Patterns
// Applied across the platform
Chain of Responsibility
// Behavioral Pattern
Every API request passes through a chain of handlers. Each handler either processes the request or passes it to the next. Used for authentication, rate limiting, sanitization, and business rule validation.
Auth → RateLimit → Sanitize → BusinessRule → Enrich
Adapter
// Structural Pattern
Each social platform has a different API format. Adapters convert incompatible interfaces (Twitter v2, Instagram Graph, LinkedIn UGC, Facebook Graph) into one unified data model.
Twitter API → IG Graph → LinkedIn → UnifiedPost
Command
// Behavioral Pattern
All post operations (create, update, delete, publish) are encapsulated as Command objects. This enables undo/redo functionality and a full history log of all actions performed.
CreateCmd → Invoker → History[] ← Undo
Observer
// Behavioral Pattern
An EventBus decouples publishers from subscribers. When a post is created/published, three subscribers react independently: AuditLogger, MetricsTracker, and NotificationSystem.
EventBus → AuditLog / Metrics / Notify

SOLID Principles
// Applied across every module in the codebase
S
Single Responsibility
Each class does one thing. User model = data only. AuthService = auth logic only. Controllers = HTTP only.
O
Open / Closed
Add a new platform adapter or event subscriber without modifying existing code. Extend, don't edit.
L
Liskov Substitution
InMemoryStore can be swapped with a MongoDB store — services won't notice. All repos share the IRepository interface.
I
Interface Segregation
Each platform adapter only implements what its platform supports. Clients don't depend on methods they don't use.
D
Dependency Inversion
Services depend on repository abstractions, not concrete classes. Injected via constructor/singleton, not hardcoded.
